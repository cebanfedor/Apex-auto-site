# Apex Auto — project notes (handoff)

Multi-page static site (vanilla HTML/CSS/JS) + Vercel serverless API + Supabase + admin CRM.
Brand: **Apex Auto** — доставка авто из США/Канады в Молдову под ключ. Founder: Федор Чебан.
Public pages in Russian; multilang RU/RO/EN via `i18n.js`.

## Run locally
```
node local-server.js            # serves static + /api on http://localhost:8081 (PORT overridable)
```
No build step. Files are served as-is. (For /api + admin you need env vars — see ADMIN_README.md.)

## Structure
- `index.html` — home: hero, calculator, economy band, "Как мы работаем", "Почему мы", lead form, free-VIN check, hot lots, reviews, FAQ.
- `auctions.html` (+`auctions.css`, `auctions.js`) — Copart/IAAI catalog via auctionsapi.com; lot detail; lead modal.
- `in-transit.html` (+`transit.js`) — «Продажа авто в пути» (бывш. `hot.html`/«Горячие», `/hot` → 301). `about.html`, `contacts.html` — inner pages.
- `styles.css` — **the whole design system** (see below).
- `script.js` — calculator logic (the core). `locations.js` — auction locations/ports data.
- `i18n.js` — translations + RU/RO/EN switcher (injected into `.mainNavV82`).
- `site-content.js` — pulls admin-editable content from `/api/content` and injects it.
- `api/`, `server/`, `supabase/`, `admin/` — backend (serverless functions, Supabase, admin CRM). **Do not break.**

## CSS conventions (IMPORTANT)
- `styles.css` was fully rewritten from scratch (v300): ~530 clean lines replacing the old 9.7k-line legacy.
- It reuses the legacy **class names / ids** (e.g. `heroV45`, `lotImportV118`, `glassSelectV152`, `apexHdrV201`, `apexProcessV205`, `apexFaqV205`) because JS depends on them — **keep these hooks when editing markup**.
- `auctions.css` is a separate stylesheet for the auctions page only.
- **Cache busting:** HTML links CSS as `styles.css?v=vNNN`. After editing CSS, bump the `?v=` query in all HTML (`index/auctions/hot/about/contacts/admin`) so browsers fetch the new file. Same for `auctions.css?v=`.
- Design tokens at top of `styles.css` (`--red:#ed0012`, neutral light bg, white cards, dark graphite accent cards, Manrope font).

## Рыночная оценка (comps) — как считается
- `action=comps` (`api/auctions.js`): оценка по РЕАЛЬНЫМ проданным лотам из
  `auctionsapi /cars?status=6` (live, не зависит от нашей флаки-базы). `fetchSoldComps`
  тянет ВСЕ страницы архива (пагинация до пустой), а не первые 300 — выборка десятки
  лотов, не «медиана по 4». **Поколение = кузов**: по году лота через `/generations`
  вычисляем ДИАПАЗОН ЛЕТ поколения (год есть у всех лотов, generation_id — только ~1/3)
  и сравниваем строго внутри него. Верх поколения НЕ открываем до текущего года; год за
  верхом самого свежего известного поколения → синтетический «новый кузов» [верх+1…тек]
  (Accord XI 2023+ ещё не в справочнике). Так Accord 2024 не мешается с 2021.
  ⚠️ **Только завершённые торги**: `/cars?status=6` помечает `sold` И живые/будущие
  лоты, где `final_bid`=текущая пред-ставка (не молоток) — из-за этого раньше
  вылезали «машины на ходу за $1500» и лоты с будущим `sale_date`. `fetchSoldComps`
  берёт лот, только если `sale_date` ≥12ч в прошлом.
  **Утиль исключён** (`isJunkLot`): титулы Non-Repairable / Cert of Destruction /
  Junk / Parts Only / Bill of Sale и повреждения Burn / Flood / Water / Biohazard —
  не возят, копеечные финалки занижали цену. **Структурно-тяжёлые исключены**
  (`isHeavyLot`): All Over / Rollover / Undercarriage / Frame / Strip — не «нормальная
  восстановимая» машина. Обычный Salvage/Rebuildable/Clear остаётся.
  **Поколения — свои `GEN_OVERRIDES` по model_id** (справочник API врёт: годы
  мировые и перекрываются — F3x 2011–2020 / G2x 2018–2022, Fusion без 2-го кузова,
  RAV4 XA50 до 2022 вместо 2025). Аудит 14.09.2026: из 375 моделей с ≥150 лотов у 213
  перекрытия/обрыв. Зашиты US-модельные годы для **275 моделей** (все модели каталога с ≥150 лотов, у которых справочник перекрывался или обрывался) (`resolveGenRange`:
  overrides → API → синтетика). ⚠️ **Справочник обрывается на 2022**: у самого
  свежего поколения `to=2022` — граница ДАННЫХ, не конец кузова → `generationsFor`
  открывает верх (`to=null`) у поколения с максимальным `from`; иначе любой 2023+
  авто получал ложный «новый кузов». Расширять по надобности (ключ = model_id).
  **Крошки/фильтр поколения — ПО ГОДУ, не по `generation_id` фида** (`attachGenRange`):
  фид относил 2018 BMW 330e к «VII (G2x)». Берём запись справочника с ближайшим
  `from` к нашему `genFrom` (±3 года, при равенстве — раньше), имя показываем
  кодом кузова как у DreamBid + US-годы («F3x · 2012–2018», «G05 · 2019–»). Нет
  записи в ±3 (U11 X1 2023, D41 Frontier 2022, RAV4 2026) → крошку поколения НЕ
  показываем — честнее, чем чужой код. Подбор «по вхождению года» — только когда
  нашего диапазона нет вовсе.
  **Диапазон поколения — универсально на ВСЕ модели**: `attachGenRange` кладёт в лот
  (detail/vin) `genFrom`/`genTo` через `resolveGenRange`. Клиент (`fetchSimilarLots`)
  фильтрует «Похожие текущие/архивные» СТРОГО по этому диапазону (тот же кузов), не
  по generation_id (в фиде пуст у свежих) и не по всем поколениям. Карточки «похожих»
  как у DreamBid: фото+цена+дата(MM/YY)+спек+состояние; цена показывается везде.
  **Топливо в «похожих» — ПРИОРИТЕТ, не жёсткий фильтр** (`fetchSimilarLots`):
  берём весь кузов (диапазон лет поколения, любое топливо), совпадающее топливо
  ставим вперёд, добираем остальными до 12. Иначе, когда своего топлива в фиде
  мало (1 активный Santa Fe Hybrid), висела одна одинокая карточка вместо десятка
  того же кузова.
  **Перцентиль ведущей цены — ПО СОСТОЯНИЮ лота** (`cq`): хороший экземпляр
  (заводится + лёгкое одиночное повреждение) = p90 своего года, средний = p68,
  убитый (не на ходу / тяжёлое) = p45. Клиент считает `cq` (good/mid/poor) по
  conditionInfo+повреждению и шлёт в comps. Так один и тот же Fusion 2017: good
  ≈ $4.2k, poor ≈ $1.6k. Перцентили ВЗВЕШЕННЫЕ и С ИНТЕРПОЛЯЦИЕЙ (при малой
  выборке ступенька прыгала $3k→$5.8k, интерполяция даёт плавно). Диапазон вокруг
  центра. Подпись «Средняя цена рынка». В ответе есть `trueMedian`.
  **Строго тот же год**: 2017→2017; окно года ширим только если своих <8. Число
  продаж НЕ показываем (малые выборки смущали). Блоки «Похожие текущие/архивные
  аукционы» фильтруют по ГОДУ+ТОПЛИВУ — реальные кликабельные лоты того же года.
  **Оценка по ПОХОЖЕСТИ, а не одна медиана на поколение** (`computeComps`): внутри
  кузова цена сильно зависит от года и пробега (свежий малопробежный ≈ вдвое дороже
  убитого). Берём проданные того же поколения (без утиля/тяжёлых) и ВЗВЕШИВАЕМ каждый
  по близости к оцениваемому лоту: `w = 1/(1+(Δлет/2)²+(Δмиль/40000)²)`. Медиана и
  p25–p75 — взвешенные; близкие по году+пробегу определяют цену, далёкие почти не
  влияют. Состояние заводится/нет **НЕ фильтр** (не на ходу ≠ плохая машина).
  Гейт поколения **АБСОЛЮТНЫЙ**: если своего поколения <4 продаж (новый 2026 Panamera)
  → null → клиент берёт агрегат `/statistics` (~$52k), а не разброс по чужим кузовам.
  Ведущее число — **диапазон p25–p75** (как DreamBid).
  ⚡ Сырой пул продаж кэшируется по make+model на 30 мин (`soldPoolCache`), страница
  `/cars` = 100 (200 весит ~1.5МБ и упиралась в 12с-abort fetchJson → мигал ok:false).
  `loadStats` в `auctions.js` вызывает comps на КАЖДОЙ странице лота; фолбэк на
  агрегат `/statistics`, если comps пусты. Фолбэк: сужаем по `engine.id` лота,
  средняя взвешена по числу продаж, диапазон = взвеш. p15–p85 СРЕДНИХ по годам/
  площадкам (НЕ абсолютные min/max — там одиночные не-продажи $1900 и пики).
  ⚠️ **Ограничение источника**: `/cars?status=6` — тонкий живой срез (для Lexus NX
  всего ~22 лота, гибридов 0), поэтому comps часто голодает → падает на агрегат.
  А `/statistics` НЕ содержит топлива: гибрид 350H и бензиновый 250 сидят в одном
  `engine.id=10` («2.5l 4») → среднюю гибрида ($≈30k) от бензина ($≈18k) не отделить.
  **Точная по-триму/топливу оценка возможна только из нашей базы `api_lots`** (там
  `fuel_id`, полная история) — как у DreamBid/BidCars. Пока БД висит (см. TODO) —
  оценка свежих/премиальных комплектаций занижена. Карточки каталога — тоже через comps
  (`forecastForLot`, 2017+), агрегат только фолбэком.
- `action=dbstatus` — read-only диагностика БД (фаза синка, sbUp, счётчики).
- Таймед/IAAI-проданные: финалку ПОКАЗЫВАЕМ (22.09.2026, снято скрытие по просьбе Федора) — источник тот же, что у истории цены по VIN.
  ценой живого молотка → путало клиентов). Прежний `action=vinfinal` (добор финалки по
  VIN через `/search-vin`) удалён вместе с UI-кнопкой «уточнить» 11.09.2026 —
  продукт решил «просто не указывать цену» на таймед/IAAI-проданных.

## Поколения — таблица `server/gen-table.js` (18.09.2026, как у DreamBid)
- **431 модель**: `[from, to(0=выпускается), код кузова]`. Источник — публичный справочник моделей DreamBid
  (коды кузова, полная история, новые кузова 2025–2026), НО границы лет там, где у нас были выверенные
  US-годы (`GEN_OVERRIDES`), оставлены наши: у DreamBid F30 «с 2013» (в США MY2012), «W214 с 2021»,
  рестайлинги местами отдельным поколением. Одинаковые коды подряд склеены, перекрытия разрезаны.
- Приоритет: **таблица → GEN_OVERRIDES (модели вне таблицы) → справочник API → синтетика**.
- Для моделей из таблицы id поколения **синтетический = from*10000+to** (`20192025`, `20250000`),
  `parseSynGen`. Фильтр каталога по нему — ПО ГОДУ (БД `year.gte/lte`, live `from_year/to_year`);
  в comps/statistics такой id провайдеру не передаём. `action=generations` отдаёт таблицу (свежие первыми).
- Год в «дыре» между поколениями → ближайшее поколение (раньше падало в самое старое).
- Смена таблицы → бамп `|g2` (`GEN_CACHE_SALT`) — кэш detail/vin/generations живёт до 6ч.

## Достоверность цен из фида (22.09.2026) — ОБЯЗАТЕЛЬНО учитывать
- Фид ставит статус `sold` (6) лотам, чьи торги ЕЩЁ НЕ ПРОШЛИ, а в `final_bid` кладёт пред-ставку. Правило: **торги в будущем →
  лот не продан**. `normalizeLot`: `preBidSold` → активный лот (`statusId 3`, пред-ставка в `currentBid`, `finalBid=0`). Синк такие
  не архивирует; старые записи базы чинит `sanitizeStoredLot` при чтении. Архив (DB и live-фолбэк) — только `auctionDate ≤ now`.
- `finalBid` НИКОГДА не додумывать из истории со статусом `not_sold` (так у BMW M4 64624966 появились «$78 000»). Только из записи со статусом продажи.
- История ставок: `not_sold` со «ставкой» >115% оценки авто или >1.5× текущего Buy Now — отбрасывать (`absurdBid`): продавец не откажется от 78k, чтобы выставить выкуп за 41.5k.
- Карточки (главная, витрины): показывать только текущую ставку / Buy Now; `finalBid` — только у лотов со статусом «продан» и прошедшей датой.
- Прежде чем объяснять пользователю «откуда цифра» — открыть сырые данные лота (detail + priceHistory) и сверить с логикой, не гадать.
- **История продаж — ТОЛЬКО по VIN** (`attachVinHistory`, `/search-vin`): номер лота пересекается между машинами и аукционами и
  меняется при перевыставлении. На странице лота priceHistory и finalBid пересобираются из VIN-данных; в списке карточек (нет VIN-
  запросов) — подпись «по этому лоту нет · полная — на странице лота», не «ранее не продавалась».
- **Одометр Канады**: Copart CA показывает КМ, а фид кладёт то же число в `odometer.mi` и «пересчитывает» в km (двойной пересчёт).
  `normalizeLot`: для канадских лотов (`location.country.iso=ca` или провинция в локации) число = км, `odometer` (мили) = ÷1.609,
  `odometerText` = «N km», `odometerUnit:"km"`. Клиент `dbOdo` показывает «км ≈ миль». В базу уходят корректные мили.
- **Правила Федора 22.09.2026 (вечер)**: (1) весь сайт проверяет историю ПО VIN в первую очередь, номер лота — второстепенно:

  только для витрины без фильтров: любой применённый фильтр (кнопка «Найти» или ссылка с фильтрами) → сортировка «Скоро торги»;
  (3) архив — строго по дате торгов, только что сыгравшие — первыми (`sale_date.desc`, синк ежечасно + лоты с прошедшей датой).
- **Свежесть архива (22.09.2026)**: поисковые ответы кэшируются ≤3 мин (память, `api_cache`, CDN `s-maxage=180`); раньше живой ответ
  лежал в `api_cache` 6ч → сыгравшие лоты не попадали в архив часами. Закрытые торги догоняет `action=syncclosed`
  (GitHub Actions каждые 10 мин, `/archived-lots?minutes=90`). Итоговый лаг «сыгралась → в архиве» ≤ ~13 мин.

## Жизненный цикл лота — требования Федора (23.09.2026, утро) и как это реализовано
1. **Показываем ВСЕ доступные лоты Copart+IAAI, США и Канада.** Замер 23.09 08:40: фид на 48ч — 76.7k, в базе было 44.9k (−40%) —
   часовой инкремент брал 3 страницы изменений на площадку и не успевал. Теперь на каждом 5-мин тике (`skipIncr`):
   (а) окно изменений `minutes=180` листается ПО КУРСОРУ `state.changes` (≤40 стр./площадку, 18с), (б) обход ближайших торгов
   `/cars?next_hours_auction=72` по курсору `state.upcoming` (до 40с). Неизменившиеся строки не переписываются (`sameKeyFields`,
   пред-чтение ключевых полей по id). Суточный полный обход (sweep) перезапускается, даже если прошлый застрял в purge >26ч.
2. **День торгов / идут онлайн** — клиент по `auctionDate` («Идут торги» до 2ч после старта).
3. **Продана → сразу «продан» + финальная ставка → архив**: `syncclosed` каждые 10 мин (`/archived-lots?minutes=30`) + `syncsettle`
   (лоты с прошедшей датой → `/search-lot` → `upsertClosedLot`). Архив = `archived=true, status 6, final_bid>0, sale_date≤now`.
4. **Перевыставили (Buy Now / новые торги) под тем же номером** → запись о продаже ОСТАЁТСЯ в архиве: перед перезаписью
   строки-продажи живой версией (или другой продажей с иной датой) копия сохраняется как `id = <auction>-<lot>-s<YYYYMMDD>`
   (`preserveSoldCopies`, вызывается из `syncUpsertRows` и из живой ветки `upsertClosedLot`). Лот снова идёт как новый, история — по VIN.
5. **Оперативно**: Vercel Cron — sync */5, closed */10, settle 5-59/10. Никаких «раз в неделю».

## Очередь онлайн-торгов Copart (24.09.2026)
- Фид отдаёт `lots[0].line`: Copart `"B/2113"`, IAAI `"1 - #40"` (у IAAI до дня аукциона `tbd`: линию назначают за ~2 часа до торгов, до этого блок скрыт (Федор: пояснение клиентам не нужно) и перепроверяется раз в 5 мин; у Timed-лотов очереди нет; на IAAI это как «Lane/Run #» на сайте аукциона). Нормализатор: `lane`, `runNo`; колонки `api_lots.lane text, run_no int` (миграция `20260924_run_line.sql`, индекс sale_date+lane+run_no).
  Синк пишет их только когда колонки есть (`runColsReady`, проба раз в 1–10 мин; иначе поля вырезаются, upsert не падает). `run_no` входит в сравнение неизменившихся строк (`keyFields`) — старые строки перезапишутся при обходе ближайших торгов.
- `action=queue&lot=<номер>` (CDN 15с, отдельное правило в `vercel.json`): лотов в линии до нашего (`before`), уже проданных из них в базе (`soldBefore`), время с начала торгов линии / 60 с (`PACE`, решение Федора: 1 машина Copart = 1 минута) → `ahead = before − max(soldBefore, byTime)`, `etaSec`, состояния
  before/queue/now/sold, последние 3 проданных и 3 следующих лота линии. «Текущего лота в эфире» и ставок в реальном времени фид НЕ отдаёт (bid обновляется редко, `bid_updated_at`) — поэтому «≈».
- Клиент: `startQueueWatch` в `auctions.js`, блок `#lotQueueV1` над калькулятором лота (Copart и IAAI, торги в окне −5ч…+30ч), опрос каждые 20 с.
- Временная диагностика `action=rawfields&auction=&lot=` — поля сырого лота фида без картинок (можно удалить).

- **Идущие аукционы (24.09.2026, Федор: «сейчас играет Калифорния, а в „Скоро торги“ Timed»)**: окно 30 мин после старта резало лоты, стоящие в очереди онлайн-аукциона (линия из ~140 лотов идёт ~2.5 ч). Теперь `api_lots.live_until`
  (миграция `20260924_live_until.sql`) = старт + (порядковый номер лота в линии × factor + margin) мин: `refresh_live_until(factor, margin)`, код зовёт с 1.3 / 10 (реальный темп Copart ≈ 76–79 с/лот); при слишком большом запасе клиент убирал по 20+ проданных карточек после старта аукциона. Номера Copart не всегда 2001…2140 (у A/831 в линии 11 лотов), поэтому позиция = `row_number()` по (sale_date, lane) в SQL-функции `refresh_live_until()`, её вызывает cron `/api/cron/engine` (каждые 3 мин). Синк колонку не пишет. Фильтры каталога (`datedLive`/`datedOrNull` в `searchFromDb`):
  лот виден, если `sale_date ≥ now` ИЛИ `live_until ≥ now` ИЛИ (`live_until` пуст И `sale_date ≥ now−30мин`); `sale_date ≥ now−6ч` — только драйвер индекса. Без колонки (`liveColReady`) — прежнее окно 30 мин. Сортировка «Скоро торги» ставит идущие лоты первыми.
  Счётчики вкладок (`tabTotal`, `computeCatalogCount`) пока считают по окну 30 мин — идущие лоты в них недосчитаны (единицы тысяч из ~440k).

- **Очередь — по статусам лотов, не по часам (24.09.2026, сверка с RideSafely: реальный лот в эфире №106, у нас было «ваш лот сейчас» №108)**: `action=queue` берёт все лоты линии из базы по `run_no`, ищет границу «завершён / ещё нет»
  пачками параллельных проб `fetchDetail` (≤4 раунда по 8 лотов, кэш проб 30 с, результат линии 45 с), отсюда `current` (лот в эфире), `ahead`, `recent` (последние 3 проданных с финалом из фида), `next`.
  Темп `pace` = прошедшее время / число завершённых лотов линии (30–150 с, при <8 завершённых — 60 с). Раньше был жёсткий 1 лот = 1 минута и «проданные» из базы с задержкой.

## Покупка по Buy Now и перепроверка лотов выкупа (25.09.2026, BMW 530e IAAI 45914882)
- Симптом: DreamBid «Продан по Buy Now $9 100 (24.09)», у нас лот «Купить сейчас $9 100». Причина: покупка по выкупу НЕ меняет основную запись лота в фиде (`status: sale`, `updated_at` 24.09 07:51, `sale_date` 28.09 от старого перевыставления),
  а только добавляет в `prices[]` раунд `sold` с «живым» временем (24.09 14:13:29, секунды ≠ 0 — не слот аукциона) и ставкой = цене выкупа. Наше правило «тот же номер лота выставлен позже → раунд не продан» (Honda Insight) превращало его в `not_sold`.
- Теперь `normalizeLot` (`bnSale`): раунд sold + секунды ≠ 0 + ставка = `buy_now` лота (±1%) + запись лота НЕ обновлялась после продажи (`updated_at ≤ дата+10 мин`) → лот продан: `statusId 6`, `finalBid`/`currentBid` = ставка, `auctionDate` = момент покупки, `saleStatus «Продан по Buy Now»`, `soldByBuyNow:true`
  (синк архивирует по этой дате; `attachVinHistory` не сбрасывает финал и не понижает такие раунды: `bnEvent`). ⚠️ Timed-раунды IAAI тоже закрываются «с секундами» — от ложных срабатываний защищает равенство ставки цене выкупа и `updated_at`.
- Крон `/api/cron/buynow` (каждые 3 мин, `action=buynowcheck`, `runBuyNowCheck`): по кругу опрашивает `fetchDetail` лотов выкупа (`buy_now>0`, не продан, дата торгов ≥ now−2ч, по возрастанию даты; курсор `alert_meta.bn_cursor`), до ≈900 лотов за тик (8 параллельно, лимит 44 с), проданные → `upsertClosedLot`.
  Лоты выкупа БЕЗ даты торгов пока не опрашиваются (только при просмотре карточки/страницы: `livebids`/`detail`).
- Превью на RO/EN (25.09.2026): язык живёт в адресе `?lang=ro|en` (`i18n.js` сам дописывает его для нерусского языка; `withLang` в auctions.js/transit.js сохраняет при навигации и в «Поделиться»). Скрейперы JS не выполняют, поэтому:
  страницы сайта → `api/page-meta.js` (rewrites с `has: lang=(ro|en)` в vercel.json; тексты и картинки — `server/og-pages.js`, PNG `assets/og/<имя>-ro.png`/`-en.png`, генератор тот же `scripts/build-og-pages.js`); каталог → `api/catalog-page.js` (lang + фильтры); лот/«в пути»/каталог/трекинг — картинки `/og/…?lang=` и описания на языке
  (`server/og-lot.js`, `og-catalog.js`, `og-track.js` — словари ru/ro/en). Новая страница/строка текста = запись в `server/og-pages.js` + `node scripts/build-og-pages.js` + бамп `?v=` картинок.
  ⚠️ `/tracking` с `?lang=` обрабатывает `tracking-page.js` сам (в page-meta не добавлять). В шрифте карточек нет «≈», «№», «→».
  Главная `/?lang=ro|en`: корень отдаёт статический index.html раньше rewrites, поэтому для превью-ботов (UA Telegram/WhatsApp/Facebook/…) — redirect на `/api/page-meta?page=index`; люди видят обычную главную.

## История продаж — почему архив «худел» и как починено (27.09.2026)
- **Причина**: формат `/archived-lots` (simple_paginate=1) изменился — запись ПЛОСКАЯ (поля лота лежат в самом item, `item.lot` — просто номер) и числа/даты приходят объектами `{value, updated_at}` (`bid`, `final_bid`, `sale_date`…). Код искал лот в `lots[0]`/`item.lot` как в объекте → дата и финал пустые → все закрытые лоты писались ЖИВЫМИ без финала
  и в архив не попадали; архив пополнял только `syncsettle` (~400 лотов/10 мин). Плюс исчезала история за дни до 21.09 (чистка/потери).
- **Исправление**: `unwrapFeedValues` (разворачивает `{value, updated_at}` → поле + `<поле>_updated_at`) и выбор лота `lots[0] || (item.lot — объект ? item.lot : item)` в `normalizeLot` и `syncRowFromItem`. `syncclosed` (*/10): окно 60 мин, до 8 страниц (пик торгов ≈ 5 тыс. закрытых/час).
- **Добор**: `?action=salesbackfill&mode=recent&minutes=4320&page=N&pages=6` (лимит фида — 4320 мин = 3 суток; повторять с `next`, лок общий с синком — при `skipped` повторить) и `mode=sold&domain=3|1` (`/cars?status=6`: у фида удерживается лишь ~12k Copart + ~4k IAAI проданных).
  Загружено 27.09: сутки-3 назад полностью (по дням: 21.09 17k, 22.09 27k, 23.09 29k, 24.09 29k, 25.09 18k; выходные 0.5k — норма); архив 162k → 174k+.
- **Контроль**: `?action=salescoverage&minutes=1440` — сколько «продано с финалом» у фида за окно (29 099 за сутки) и какой % уже в нашем архиве (по выборке 1800; 100%), «застрявшие» живые строки 6–72 ч назад (`stale.past6to72h` ≈ 11.8k — в основном непроданные раунды, ждут перевыставления). Дни до ~20.09 в архиве неполные (у 15–18.09 по 1–4k при норме 20k+).
  Дальше в прошлое фид отдаёт только всё сразу без окна: `/archived-lots` без `minutes` = 2.4 млн записей с апреля (порядок не по дате) — заливать целиком в Supabase Micro (8 ГБ) нельзя без решения Федора (объём и стоимость).
- Диагностики: `archprobe` (параметры окна фида), `salescoverage`, `salesbackfill`.

## Ориентир ставки — ACV из фида (26.09.2026, Федор: «использовать оценочную стоимость лота»)
- Изучены DreamBid и BidCars: их «Оценочная стоимость» (DreamBid `avg_final_bid`, публичный `app.dreambid.pl/api/lots/<key>`) — это СВОИ comps (медиана/диапазон похожих проданных лотов), а НЕ производная от ACV
  (actual_cash_value): на живых лотах ratio final/ACV у них 7–53%, разброс большой — «слух про 50–60% от ACV» не подтвердился как общее правило, только для почти целых машин.
- **Калибровка по НАШЕЙ базе** (`?action=acvcalib`, читает `payload->>estimatedRetailValue`/`airbags`/`keys` у архивных лотов с ACV, ~5300 продаж на выборке 6000): медиана finalBid/ACV по состоянию (`conditionCoef`) —
  1.10 (почти целая) → 0.42, 1.00 → 0.29, 0.90 → 0.27, 0.85 → 0.23, 0.80 → 0.21, 0.75 → 0.19, 0.70 → 0.18, 0.60 → 0.17, 0.50 (утиль-документ) → 0.16. Сработавшие подушки → ×0.8, нет ключей → ×0.6 (данные: 0.128 против 0.278, у нас консервативнее).
  Пробег двигает долю ДАЖЕ поверх ACV (она не идеально его учитывает): 0–30к миль ×1.15 … 150к+ ×0.65 (`acvMileageAdj`). Все числа — `server/price-guide.js` (`ACV_RATIO_BY_COEF`, `acvMileageAdj`, `acvExtraAdj`, `estimateFromAcv`), тесты — `test/price-guide.test.js`.
- **Где используется**: только в «data»-ветке `computeCompsForQ` (модели ВНЕ таблицы Федора — её саму не трогали, приоритет 1 как был). Похожих продаж по кузову ≥6 → смешивается с comps-медианой (вес ACV 0.25–0.45 по числу похожих, `src:"data+acv"`); <6 похожих → раньше грубое усреднение всего пула (`dataGuideBase`), теперь чистый ACV-ориентир (`src:"acv"`), если ACV есть.
  Наружу разницы нет — ответ `action=comps` как был `{guide:true, src, p25, p75, median}` (клиент не менялся). Клиент теперь шлёт `acv` (ACV лота), `airbags`, `keys` в `compsParamsFor` (auctions.js) — идёт и в одиночный `action=comps`, и в `compsbatch` для карточек каталога.
- **Проверка `?action=compstest`** (расширен блоками `acv`/`blend` — тот же вес-по-count, что в проде): RAV4 медианная ошибка comps-only 28%→ с ACV 18% (within25% 46→59), Camry 36→28% (40→46), BMW 3 55→44% (25→35) — заметное улучшение на популярных моделях.
  Порше Panamera (тонкий пул, n=8) — на грани шума, чуть хуже; вес ACV в смеси снижен с 0.55 до максимум 0.45, чтобы не рисковать тонкими пулами.
- **Живой пример находки** (IAAI 66261236, 2022 Porsche Panamera Base, ACV $66 124, Minor Dent/Scratches, 45 806 миль): раньше усреднение по всему пулу поколения (4 старых Panamera 2017–2018) давало медиану $16 231 —
  занижало свежий кузов вдвое. Теперь по ACV — $26 700–36 100. Тест на этом лоте — `test/price-guide.test.js`.
- Метод оценки в ответе (`match.gen`/`src`) наружу как был — клиенту не показываем, откуда цифра (правило: наружу только `{guide:true, src, p25, p75, median}`).

## Аудит по маркам — Audi/BMW/Mercedes/Toyota/Lexus/Ford/Lincoln + гибриды-электро 2017+ (27.09.2026)
- **Прогон `?action=compstest` по 54 моделям** (~15 тыс. leave-one-out проверок на реальных продажах): медианная ошибка была comps-only 47% → со смесью ACV 38%; там, где есть таблица Федора — 58% → 31% со смесью. Хуже стало только на 5/54 (в пределах шума маленьких выборок).
- **Нашёл и починил реальный баг**: `fetchSoldCompsFromDb` (пул для comps И для `?action=compstest`) шёл без `ORDER BY` — Postgres без явного порядка мог на разных запросах отдавать разные строки, из-за чего повторные прогоны `compstest` для ОДНОЙ И ТОЙ ЖЕ модели давали разные цифры (не воспроизводилось). Добавлен `order=sale_date.desc` — теперь результат стабилен между запросами. На живую оценку (`computeComps`, берёт весь ответ) это не влияло, только на диагностику.
- **Динамический вес ACV в смеси с таблицей** (`guideAcvWeight` в api/auctions.js): было фиксированных 0.3, теперь растёт (до 0.65), если таблица и ACV лота сильно расходятся между собой — типичная ситуация у марок, где таблица завышает. Эффект: Ford Fusion таблица-ошибка 148%→57% (было 79% при фиксированном весе), BMW 65%→30% в среднем, Mercedes 42%→22%.
- **Audi — единственная марка, где проблема осталась после всех правок**: A4 190%→73%, A3 147%→87% (`actualToGuideRatio` 0.35–0.41, таблица завышает в 1.6–2.4× — самое сильное расхождение из всех проверенных марок). ACV-оценка сама по себе для Audi тоже слабая (52% ошибки) — не может полностью скорректировать. Похоже, дело либо в конкретных строках таблицы для Audi, либо ACV из фида у Audi ведёт себя иначе, чем у остальных марок (нужна проверка Федора — цифр таблицы не вижу).
- **`?action=acvcalib&make_id=<id>`** (новый фильтр) — калибровка finalBid/ACV по конкретной марке. Нашёл: у BMW реальное отношение выше общего (coef 1.00 → 0.36 против общих 0.29) — марка продаётся дороже относительно своей ACV, чем среднее по каталогу; у Audi отношение близко к общему. ## Гибриды/электро/plug-in — comps теперь по VIN, а не по сырому топливу фида (27.09.2026)
- **Нашёл**: `computeComps`/`dataGuideBase` (пул похожих продаж для «Ориентира ставки») фильтровали топливо по сырому `fuel_id` фида — той же колонке, которая путает гибрид/plug-in/mild-hybrid (весь смысл `fuel_x`). Лот, оцениваемый по VIN как «гибрид», мог сравниваться с пулом, где часть строк на самом деле plug-in — искажало цену.
  Плюс `FUEL_TEXT_TO_ID` маппил `phev`/`plug-in` на тот же код 3, что обычный гибрид (легаси, до fuel_x) — из-за этого даже правильно определённый plug-in лот при подборе похожих сравнивался с обычными гибридами.
- **Исправлено**: `effFuel(r) = fuel_x || fuel_id` — везде, где пул фильтруется по топливу (comps, dataGuideBase, compstest). `resolveFuelText(q)` — сервер предпочитает `fuel_x`, присланный клиентом (`lot.fuelKind` через `compsParamsFor`), сырому `lot.fuel` тексту. `phev` теперь код 5, отдельно от гибрида (3).
- **Тест**: `?action=compstest&…&fuel=hybrid|phev|electric` — фильтрует и целевую выборку, и пул похожих по эффективному топливу. Прогон (27.09.2026): гибриды в целом ведут себя как остальной каталог (Prius/RAV4/Camry/NX blend-ошибка 16–24%, Sienna table 48%→14% с ACV); Ford Fusion Hybrid — тоже самый больной (table 157%, как у бензиновой версии, тот же проблемный ряд таблицы). Plug-in почти нигде не набирается для честного leave-one-out (2–5 проверок на модель) — архивных PHEV-продаж с известным топливом пока мало.
- **Нашёл вторую, более крупную причину слабого покрытия**: фоновая заливка `fuel_x`/`vin_trim` (`runPowertrainFill`, крон `/api/cron/powertrain` раз в 2 мин) обрабатывала ТОЛЬКО `archived=false` (живые/ближайшие лоты) — архив (174k+ проданных, это и есть пул для comps) почти не имел fuel_x вовсе. Добавлена вторая фаза очереди по архиву (свежепроданные первыми, `sale_date.desc`), делит бюджет прогона (65% живым лотам, остаток архиву).
  Индекс — `supabase/migrations/20260927_fuelx_archived_idx.sql` (`idx_lots_vintrim_archived_todo`, `idx_lots_fuelx_archived_todo` + `analyze`), **выполнен Федором 27.09.2026 вечером**.

## Фикс модели Tesla не срабатывал, если фид путал ещё и МАРКУ (28.09.2026, Федор, тот же лот IAAI 40084037: «зашёл с каталога по Канаде, а в хлебных крошках Subaru/Impreza», реально Tesla Model Y)

## Пул похожих продаж (comps) теперь учитывает СОСТОЯНИЕ, а не только год/пробег (28.09.2026, Федор, Tesla Model Y Copart 59336256: «вилка до $31 700 — супер дорого, я думаю 19-24, но никак не 30+»)
- **Причина**: `computeComps` (api/auctions.js, ветка «data» — модели вне таблицы Федора) взвешивал пул проданных ТОЛЬКО по близости года и пробега к оцениваемому лоту; состояние/повреждения самого лота в отборе ПУЛА вообще не участвовали — влияли лишь на то, с какого перцентиля этого пула брать итоговую цифру (`centerP`: good→90, poor→45, mid→68, верх = `centerP+20`). Из-за этого у битого лота (Structural, две зоны) верхняя граница вилки (высокий перцентиль) выдёргивалась из почти целых экземпляров того же года/пробега — те же машины наравне с битыми тянули верх пула вверх.
- **Исправление, два слоя (оба в `computeComps`)**:
  1. **Сужение пула** — если строк с данными о повреждениях (из нашей БД, `fetchSoldCompsFromDb`, поле `dmg`) достаточно (≥6) в окне близости коэффициента состояния (`conditionCoef`, та же шкала, что у таблицы Федора/ACV — не грубый bucket good/mid/poor, а непрерывное число), дальше сравниваем ТОЛЬКО с ними. Окно расширяется 0.1→0.2→0.35, пока не наберётся 6 (тот же приём, что уже был для года/топлива). Мало похожих по состоянию — пул остаётся широким, как раньше (лучше вся история кузова, чем 5 случайных).
  2. **Довес по состоянию внутри пула** (`wOf`) — даже без полного сужения (например, окно расширилось и часть «чужого» состояния всё же попала) каждая строка дополнительно взвешивается по близости `conditionCoef` к целевому, наравне с годом/пробегом (0.15 ≈ один шаг шкалы состояния — совпадающее не трогает вес, дальнее почти обнуляет).
  - Живой фолбэк (`fetchSoldCompsLive`, когда БД недоступна) повреждений не отдаёт вовсе (`r.dmg === undefined`) — для таких строк оба слоя пропускаются, поведение как раньше (только год/пробег).
- **Коэффициент состояния (`meta.coef`)** прокинут во все 3 места, где вызывается `computeComps`: основная ветка `computeCompsForQ` (уже был в скоупе — `coef`, считался для guide/ACV), запасная ветка той же функции (посчитан заново из `q.get(...)`, был вне скоупа try-блока), leave-one-out тест `?action=compstest` (коэффициент ИСКЛЮЧЁННОГО лота — вычисляется один раз и переиспользуется, заодно убрал 3 дублирующихся вычисления `cf`).
- В ответ `computeComps` добавлено `match.condition` (сузился ли пул по состоянию) — для диагностики, наружу клиенту как было (`p25`/`p75`/`median`/`trueMedian`).
- Тесты — `test/comps.test.js` (новый файл, требует `computeComps` из `api/auctions.js` — довешена в `module.exports.computeComps` отдельным свойством, вызов handler'а как функции это не задевает): воспроизводит баг без `coef` (верх вилки застревает в кластере «целых»), проверяет сужение пула с `coef` (верх остаётся в кластере похожего состояния), проверяет отсутствие падения на строках без данных о повреждениях (живой фолбэк).

## Бейдж «ставка выше ориентира» называл не то значение (28.09.2026, Федор, Tesla Model Y Copart 64229956, 2026 год · 1423 мили)

## Заявки (лиды) падали — пропал UNIQUE на customers.phone (01.10.2026, Федор со скриншота)
- Симптом: модалка «Получить расчёт по лоту» → «Не удалось отправить заявку». `handleLead` отдаёт 400.
- Причина (найдена временным флагом `__diag` в ответе 500/400, потом убран): `supabase.upsert("customers", …, on_conflict=phone)` требует UNIQUE-констрейнта на `customers.phone`, а он **пропал** (обслуживание/восстановление базы) → Supabase 400 «there is no unique or exclusion constraint matching the ON CONFLICT specification». `leads` создавались бы (там обычный `create`), но падали раньше — на шаге клиента.
- Фикс (код, без ожидания БД): `handleLead` теперь **«найти-или-создать»** клиента — `supabase.list("customers", {phone:eq.…, limit:1})` → иначе `create`. Не зависит от констрейнта, заявка не теряется. Небольшой риск дублей клиента при гонке двух заявок с одним телефоном (без констрейнта INSERT не атомарен) — приемлемо: лучше дубль, чем потерянный лид.

## Постоянная страница /vin/<VIN> — индексация по VIN-запросам (05.10.2026, Федор: «хочу попадать в поиске по VIN, как BidCars»)
- **Причина**: гугл не находит наш сайт по VIN (проверено на реальном запросе: BidCars/польские/румынские/украинские сайты
  выдаются, мы — нет), хотя страница лота (`/auctions/<slug>`) содержит VIN и неплохо оптимизирована (SSR, JSON-LD Car+Offer).
  Две причины: (1) страницы лотов НЕ в sitemap.xml — гугл находит их только через случайный краул по ссылкам из каталога,
  который сам меняется каждую минуту; (2) страница лота умирает вместе с лотом (продан/снят с торгов → 404 или другие
  данные под тем же URL) — даже проиндексированная страница быстро теряет актуальность и перестаёт отвечать на запрос.
  BidCars и конкуренты обгоняют не умом, а постоянными архивными страницами по VIN, которые живут годами.
- **Решение**: отдельная страница `/vin/<VIN>` (`api/vin-page.js`, шаблон `vin.html` — без `auctions.js`/калькулятора,
  чисто SSR-контент + стандартный шаблон хедер/футер + `auctions.css` для визуального языка таблиц/бейджей), которая
  НЕ привязана к конкретному лоту и не исчезает, когда он продан — только растёт в авторитете.
  - Источник данных — новый `action=vinarchive` в `api/auctions.js`: (1) живой `fetchVin` (факты о машине) +
    `attachVinHistory` (ПОЛНАЯ история по всем заходам, не только текущему раунду — её сознательно не делает `action=vin`,
    чтобы не удваивать fetch и не грузить лишним каждый VIN, вставленный в калькулятор на главной); (2) если фид не знает
    VIN (старый лот) — фолбэк на то, что уже накоплено в `vin_hist` (таблица существует с 24.09.2026, копится при КАЖДОЙ
    проверке VIN на сайте — карточки каталога, страница лота, алерты, Clean Select). Если нет ни того, ни другого —
    честный `404 + noindex` (не плодим тонкие страницы под случайные/несуществующие VIN).
  - Контент: факты о машине (если известны — фото, год/марка/модель, характеристики), ссылка на текущий активный заход
    (если лот снова на торгах), таблица ВСЕХ известных заходов (дата, аукцион+лот со ссылкой на `/auctions/<auction>-<lot>`,
    статус, ставка), CTA «Оставить заявку». JSON-LD — `Car` (через `lotJsonLd`, если есть живой `lot`, иначе лёгкий stub
    с одним `vehicleIdentificationNumber`). RU/RO/EN через `?lang=` — свой словарь TXT внутри `vin-page.js` (не через
    `i18n-dict.js`: страница рендерится ДО клиентского JS, Google должен видеть готовый текст на нужном языке сразу).
  - Канонический адрес — VIN заглавными буквами, нижний/смешанный регистр → 301.
- **Сайтмап**: объём растёт каждый день (vin_hist копится сам) — статический `sitemap.xml` для этого не годится.
  Отдельный ДИНАМИЧЕСКИЙ `api/vin-sitemap.js` (читает `vin_hist`, фильтр `rounds_n > 0` + валидный VIN, лимит 5000 —
  старт консервативный, расширять по факту индексации через Search Console Coverage), подключён ВТОРОЙ строкой
  `Sitemap:` в `robots.txt` (сам `sitemap.xml` не трогали, чтобы не рисковать статическими 76 URL).
- **Внутренняя ссылка**: на странице лота в строке «VIN» (рядом с копи-чипом) добавлена ссылка «История по VIN →»
  на `/vin/<VIN>` — для органического краула (не только через sitemap) и чтобы сами пользователи видели полный архив.
- Проверено: headless-прогон `api/vin-page.js` напрямую (мок `action=vinarchive`) — живой фид с фактами (200, индексируется,
  JSON-LD Car, ссылка на текущий лот), фолбэк на кэш без фактов (200, индексируется, таблица из того что есть),
  неизвестный VIN (404+noindex), некорректный формат VIN (404+noindex, фид вообще не дёргаем), регистр VIN (301 на
  заглавный канонический адрес), RO/EN рендер (`html lang`, заголовок, H1 — на нужном языке). `api/vin-sitemap.js` —
